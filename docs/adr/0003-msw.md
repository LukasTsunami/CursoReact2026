# 0003 - Mock de API com MSW (Mock Service Worker)

## Status

Accepted

## Contexto

O curso "Escolha de Poltronas de Teatro" precisa ensinar `fetch`/`useEffect`
(a partir da fase-5, `GET /api/layout`) e envio de formulário (fase-9,
`POST /api/pedidos`) sem depender de um backend real — não há orçamento de
aula para subir e manter um servidor, e o projeto é distribuído como 10
pastas independentes que precisam rodar sozinhas com `npm install && npm run dev`.

Ao mesmo tempo, o critério de corretude do curso (Principle II — Testes Como
Juiz) exige que a mesma lógica de busca de dados usada no navegador também
seja exercitada nos testes automatizados, sem duplicar a definição dos mocks
em dois lugares.

## Decisão

Usar **MSW (Mock Service Worker)** como camada única de mock de API.

MSW intercepta `fetch` no nível de rede real: no navegador via Service
Worker (`setupWorker`, `src/mocks/browser.ts`), e nos testes via
`setupServer` (mesmos handlers de `src/mocks/handlers.ts`). Isso permite
ensinar `fetch`/`useEffect` como se houvesse uma API de verdade, sem exigir
um processo de backend separado.

Os handlers já existem em `src/mocks/handlers.ts` desde a `fase-0`
(boilerplate preparado), mesmo sem serem chamados pela UI antes da fase-5 —
o mesmo padrão adotado para o React Router nesta feature (biblioteca
presente e funcional cedo, virando matéria de aula só depois).

## Consequências

- **Positivas**: um único conjunto de handlers serve navegador e testes, sem
  duplicação de lógica de mock; o aluno aprende `fetch` como se fala com uma
  API real, incluindo estados de loading/erro (`FR-007`); nenhum processo
  externo precisa ser iniciado para rodar `npm run dev` ou `npm test`.
- **Negativas**: exige entender o conceito de Service Worker para depurar
  problemas de interceptação no navegador (registro do worker, cache do
  browser); o comportamento de polling (fase-6+) precisa de um sorteio
  determinístico sob teste (seed/flag injetável no handler) para não deixar
  a suíte instável — ver `research.md`.

## Alternativas consideradas

- **Mocks manuais de `fetch` com `vi.fn()`**: rejeitado — não reflete
  tráfego de rede real e exige duplicar a lógica de mock entre navegador e
  teste.
- **`json-server`**: rejeitado — é um processo externo separado, o que
  complica o passo único `npm install && npm run dev` que cada uma das 10
  fases precisa preservar isoladamente.

## Quando reconsiderar

Se em algum momento existisse um backend real para o front-end apontar, MSW
deixaria de fazer sentido — ele existe justamente porque não há um. Nesse
cenário, a camada de mock seria substituída por chamadas diretas à API real
(possivelmente mantendo MSW só nos testes, como um "test double" clássico).
